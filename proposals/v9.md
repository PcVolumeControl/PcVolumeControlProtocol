# Proposal: v9, pairing and binary framing

Status: draft for discussion. Nothing here is implemented.

This builds on the reworked v8 in [v8-rework.md](v8-rework.md). The message
types and their members stay the same. What changes is underneath them: who
is allowed to connect, how the bytes are protected, and how they are framed.

Like v8, it is a clean break. A v9 side does not talk to an older one.

## Goals

- Only devices the user has paired can read the mixer or change it. Today
  anything that can reach the port can do both, and session details put
  browser tab titles on the wire.
- Nobody else on the network can read or alter the traffic.
- Icons travel as bytes, not base64.

Not goals: access from outside the local network, user accounts, or
protection against software already running on the PC or the phone.

## Connection

1. The client connects to TCP port 3000.
2. The server sends one JSON line in the clear:

   ```json
   {"type":"hello","protocolVersion":9,"applicationVersion":"v12","serverName":"wiglaf","serverId":"k3f9x2mq"}
   ```

   It exists so that an older app, which reads lines of JSON, can see the
   version and tell the user to update. It carries nothing private.
3. The client starts a TLS 1.3 handshake on the same connection.
4. Everything after that is framed messages inside TLS.

## Frames

A frame is a 4-byte big-endian length followed by that many bytes of CBOR
(RFC 8949): one map with text keys, using the same member names as the v8
JSON messages.

In CBOR diagnostic notation, the frame for a master volume change holds:

```
{"type": "setMaster", "volume": 64.0}
```

- `data` in an `icon` message is a CBOR byte string holding the PNG. No
  base64, so an icon costs its own size and nothing more.
- Limits: 64 KiB for a frame from a client, 1 MiB for one from the server.
- Text keys keep the messages readable with any CBOR diagnostic tool, and
  keep the v8 documentation valid as the description of each message. Integer
  keys would save a few bytes per message and are not worth that.
- As in v8, both sides ignore members and message types they do not know.

A small command-line tool in the server repository would print a live
connection as text, to replace what `nc` does for JSON today.

## Trust

**The server** creates a self-signed certificate the first time it runs. Its
identity is the SHA-256 of the certificate's public key, the *fingerprint*.
Clients never check the certificate against a certificate authority; they
check that the fingerprint is the one they paired with. `serverId` in the
greeting and in mDNS is a short form of the fingerprint, so a client can
recognise its PC after the address changes.

**A client** receives a random 32-byte token when it pairs, and stores it
with the server's fingerprint in the platform's secure storage. On every
later connection it verifies the fingerprint during the TLS handshake and
then sends the token in its `hello`:

```
{"type": "hello", "protocolVersion": 9, "clientName": "Pixel 8",
 "clientId": h'9A41…', "token": h'5C0E…'}
```

The server answers with `state`, or with the fatal error `unauthorized`. An
unpaired connection may send pairing messages and nothing else.

The server app lists paired devices with when each was last seen, and can
revoke any of them.

## Pairing

The server accepts pairing only while its "Pair a device" screen is open, for
a couple of minutes at a time. Two ways in, both ending with the client
holding the fingerprint and a token.

### By QR code

For phones. The PC shows a QR code containing the address, the fingerprint
and a one-time secret:

```
pcvc://pair?host=192.168.1.46&port=3000&fp=…&secret=…
```

The phone scans it, connects, checks the fingerprint in the TLS handshake and
sends the secret:

```
{"type": "pair", "clientName": "Pixel 8", "clientId": h'9A41…', "secret": h'…'}
{"type": "paired", "token": h'5C0E…'}
```

Nobody can sit in the middle, because the fingerprint reached the phone
through the screen and not through the network.

### By comparing a code

For clients with no camera: a desktop client, or a small device with a
display. The client connects and accepts whatever certificate it is shown,
remembering its fingerprint. Then:

```
client  {"type": "pairStart", "clientName": "Desktop", "clientId": h'…', "commit": h'…'}
server  {"type": "pairChallenge", "nonce": h'…'}
client  {"type": "pairReveal", "nonce": h'…'}
```

`commit` is the SHA-256 of the client's nonce, sent before the client learns
the server's nonce. Both sides then compute a six-digit code from the
fingerprint and the two nonces. The PC shows "Desktop wants to pair: 482 913"
and the client shows its own code. The user confirms on the PC that they
match, and the server sends `paired` with the token.

If someone is in the middle, the client saw their certificate, so the two
codes are computed from different fingerprints. Committing to the nonce first
stops the attacker from picking values that make the codes agree anyway: they
get one blind guess in a million per attempt, and the pairing screen allows
only a few attempts.

## What stays the same

Every v8 message and rule: `state`, `update` and revisions, the commands,
`getIcons` and its limits, `error` codes, session details. A v8 client's
state handling carries over untouched; only the layer that turns bytes into
messages is replaced.

## What it protects against

| Threat | Covered |
| --- | --- |
| Another device on the network changing the volume | Yes |
| Another device reading tab titles or app names | Yes |
| Someone recording Wi-Fi traffic | Yes |
| Someone in the middle after pairing | Yes: the fingerprint will not match |
| Someone in the middle during QR pairing | Yes |
| Someone in the middle during code pairing | Yes, up to a one in a million guess per attempt |
| A person at the unlocked PC pairing their own phone | No |
| Software already running as the user on the PC or phone | No |
| Flooding the port with connections | No |

## What it costs to build

| Where | Work |
| --- | --- |
| Server | Certificate creation and storage, TLS (rustls), frame codec, token store, the pairing screen with a QR code, a paired devices list with revoke. |
| Android, KMP | TLS with a trust check against the stored fingerprint, a CBOR codec (kotlinx.serialization has one), secure storage, pairing screens, a QR scanner and the camera permission that goes with it. |
| iOS | The same, with Network.framework's verify block for the fingerprint and the Keychain for storage. |
| ESP32 | MicroPython's TLS support is limited. This client may have to stay on an older server. |
| This repository | PROTOCOL.md gains the transport and pairing chapters; examples in CBOR diagnostic notation. |

The rollout constraint is the same as for v8: the Rust server has to be the
released, working server on Windows first, because new apps stop talking to
the C# one.

## Open questions

1. **Is encryption needed, or only authentication?** A much smaller step
   keeps v8's JSON lines and adds the token with a challenge and response at
   connect. It stops other devices from controlling the mixer, but traffic,
   tab titles included, stays readable to anyone recording the network.
2. **Token or client certificates.** Mutual TLS, where the client presents a
   certificate created at pairing, removes the token from the messages. It is
   more work with the phone platforms' TLS APIs.
3. **QR, code, or both.** QR is the easier ceremony on a phone and needs a
   camera permission. The code works everywhere and needs two screens' worth
   of interface on each client.
4. **Is CBOR worth a new dependency in every client?** The alternative keeps
   JSON for messages and adds one byte to the frame header saying "this frame
   is raw icon bytes". That gets icons out of base64 with no new encoding.
5. **Unpaired access as a setting.** Some people will not care who on their
   network can change the volume. An "allow any device" switch on the server
   is cheap, and it weakens the default story.
6. **Reinstalling the server** creates a new certificate, so every client has
   to pair again. Exporting and importing the identity would avoid that.
